## Description

LLM calls go through terva, not straight to a provider. docs/BRIDGE-PROTOCOL.md section 9
names two ways in:

- Embed terva through the Go SDK (`packages/agent/sdk`), with the task menu
  offered as tools.
- Make the controller a terva connector extension, so Valheim chat is a
  connector like the Discord bridge, and the same process provides the tasks as
  tools.

`terva rpc` as a child process is a third option if isolation matters more
than a single binary. Read terva's docs/embedding.md, docs/connectors.md and
docs/personas.md, then pick one.

## Acceptance criteria

- [x] The chosen integration is recorded with the reason, against the alternatives
- [x] It shows where the persona and provider configuration live
- [x] It shows how the task menu reaches the model as tools
- [x] It shows that every proposed task still passes the controller's validation before reaching the plugin

## Summary

Decision: embed terva through its Go SDK, `terva.sh/terva/packages/agent/sdk` at
v0.141.5 (MIT). Checked on 2026-10-28 against the terva checkout at
v0.141.4+69, and `go get terva.sh/terva@v0.141.5` resolves with no replace
directive.

### How it fits

- **Call:** `sdk.New(sdk.Config{...})` returns a `*sdk.Runtime`, and
  `rt.Prompt(ctx, text, nil)` returns a channel of `sdk.Event`. Reply text
  arrives as `text_delta` events. Cost comes from `rt.Cost()`.
- **Task menu as tools:** `Config.ExtraTools []core.Tool`, one per allowed
  task, with `NoTools: true` so terva's own read/write/bash tools are absent,
  and `MaxSteps: 2`. A tool's `Execute` only records a proposal; it never
  acts. The first proposal in a turn wins, and any later one gets an
  `IsError` result. terva has no option to cap tool calls, so the controller
  enforces "at most one".
- **Validation:** the recorded proposal goes through the same path as a
  grammar command: owner check, then `allowedTasks` ∩ `capabilities`, then
  `protocol.TaskRequest.DecodeArgs`. Only then is it sent to the plugin. The
  model never reaches the plugin directly.
- **Persona:** renki's own config (`llm.persona`), passed as
  `Config.SystemPrompt`, which outranks terva's persona files. The SDK
  exposes no persona or chat-mode field.
- **Provider, model and key:** `Config.Provider`, `Model` and `APIKey`, from
  renki's `llm.terva` config block. Anything left empty falls back to
  `$TERVA_HOME/config.json` and the provider's environment variables, as the
  terva CLI does. `Yolo: true` is set, so the machine's permission rules and
  classifier don't apply to our record-only tools.
- **History:** the SDK keeps no sessions. Every prompt is built fresh from
  the state summary and the last ~20 chat lines, and `SetMessages(nil)` runs
  before each prompt. Cooldowns are per player; the daily cap comes from
  `rt.Cost()`.

### Against the alternatives

- **Connector extension:** rejected. The tunnel is experimental, terva would
  own the process and the per-chat sessions, and its pairing, `/stop` and
  `/status` overlap our grammar and owner list. terva would also have to be
  installed on the VM.
- **`terva rpc` as a child process:** rejected. It has the most stable
  protocol, but our tools would have to live in an extension or an MCP
  server outside the controller, and the binary would be needed on the VM.
  Isolation buys little when the tools never execute anything.

### Costs

- **Go version:** terva's go.mod says go 1.27.0, so renki's go directive
  rises from 1.25.0 to 1.27.0. The toolchain auto-downloads (go1.27.3
  checked). terva counts a Go bump as breaking, so we follow its releases.
- **Size:** the dependency is heavy, about 75 terva packages. A Windows build
  of the SDK example was 27 MB.
- **Isolation:** the LLM lives in its own package (internal/voice) behind an
  interface, so the grammar path and tests never import terva.
